1. project.yml — Ceedling Unit Test Config
tests/unittest/project.yml belongs to Ceedling, a Ruby-based unit test framework for C built on Unity (test runner) and CMock (auto-generated mocks).

It is not a build config for the firmware itself — it only governs your host-side unit tests under tests/unittest/. Key things it configures:

Where to find test files (test/**) and source files (../../src/**)
The UNIT_TEST preprocessor define, so you can #ifdef UNIT_TEST to exclude hardware-dependent code
CMock behavior (strict ordering, mock prefix, type handling)
gcov code coverage settings
You run tests with: cd tests/unittest && ceedling test:all

2. CMake → CMakeLists.txt → Ninja
These three work as a two-stage build pipeline:


CMakeLists.txt  (describes WHAT to build)
      ↓  cmake configures
  build.ninja   (generated build graph)
      ↓  ninja executes
  BlinkLED.elf / .hex / .bin
CMake reads CMakeLists.txt and generates the build/build.ninja file. It does not compile anything itself — it just generates the recipe.

Ninja is the actual build executor. It's a minimal, fast build system designed to be generated by tools like CMake, not hand-written. It reads build.ninja and runs the compiler commands in parallel.

The two commands from commands.txt:


# 1. Configure: generates build/build.ninja
cmake -DCMAKE_BUILD_TYPE=Debug -S . -B build -G Ninja -DCMAKE_TOOLCHAIN_FILE=arm-none-eabi-gcc.cmake

# 2. Build: runs the ninja build
ninja -C build
arm-none-eabi-gcc.cmake is the toolchain file — it tells CMake to use arm-none-eabi-gcc instead of the host gcc, targeting Cortex-M4 with FPU (-mcpu=cortex-m4 -mfpu=fpv4-sp-d16 -mfloat-abi=hard).

3. clang-tidy and clang-format
Both tools are configured via files at the workspace root and driven by the run-clang-* wrapper binaries installed in the Docker image (from the lmapii GitHub project).

clang-format — auto-formats code style:

Config: .clang-format — 4-space indent, 120-column limit, custom brace wrapping, etc.
Scope file: clang-format.json — targets ./src/**, ./include/**, and test files
Run it: run-clang-format --config clang-format.json (inside the Docker container)
To apply fixes in-place: run-clang-format --config clang-format.json --fix
clang-tidy — static analysis / linting:

Config: .clang-tidy — bugprone-*, readability-*, and misc-* checks enabled; most are also WarningsAsErrors
Scope file: clang-tidy.json — targets only ./src/**, uses ./build as the build root (needs compile_commands.json from it)
Requires a prior CMake configure step so build/compile_commands.json exists (enabled by CMAKE_EXPORT_COMPILE_COMMANDS ON in CMakeLists)
Run it: run-clang-tidy --config clang-tidy.json
Both tools are wrappers that glob files and call the real clang-format/clang-tidy binaries, which are LLVM 16 installed in the container.

4. CubeMX Integration
CubeMX is ST's GUI code generator. The integration here is file-based, not automated:


CubeMX/              ← everything in here was generated by STM32CubeMX
├── CubeMX.ioc       ← the project config file you open in CubeMX GUI
├── Core/Src/main.c  ← generated HAL init + clock config
├── Core/Inc/        ← generated headers
├── Drivers/         ← HAL + CMSIS libraries
├── Middlewares/     ← FreeRTOS source (placed here by CubeMX)
├── STM32F407XX_FLASH.ld  ← linker script
└── startup_stm32f407xx.s ← startup assembly
The root CMakeLists.txt manually references all the CubeMX-generated files by path. When you re-generate from CubeMX, you may need to update CMakeLists.txt if new source files were added.

There are actually two CMakeLists: the root one (your actual build) and CubeMX/CMakeLists.txt (CubeMX's own generated build file, not used by your main build — it exists for CubeMX's internal preview/test builds).

5. FreeRTOS Configuration in CubeMX
Yes, you configure basic FreeRTOS settings in CubeMX — but only a subset:

Configured in CubeMX	Configured manually
Enable/disable FreeRTOS middleware	FreeRTOSConfig.h parameters (heap size, tick rate, stack sizes)
CMSIS-RTOS v2 wrapper on/off	Task priorities and stack sizes for your custom tasks
Default task creation	Which heap implementation (heap_4.c here)
Timebase source (TIM7 here, not SysTick — needed because HAL needs SysTick, FreeRTOS needs SysTick too)	
Looking at your CubeMX.ioc, CubeMX configured:

FreeRTOS with CMSIS-RTOS V2
TIM7 as the HAL timebase (so SysTick is free for FreeRTOS)
A defaultTask with 128-word stack at priority 24
After re-generating, CubeMX writes FreeRTOSConfig.h into CubeMX/Core/Inc/ — that's where you tune the deep FreeRTOS knobs. Your own tasks (src/tasks/blink_led.c) are in the src/ tree outside CubeMX so they survive regeneration
